Cómo sincronizar mi web entre GitHub y Apache sin perder cambios

Una guía para mantener al día el repositorio de Internet, la copia Git del ordenador y la web que pruebas en localhost.

1. Las tres copias de tu web

En nuestro proyecto no hay una sola carpeta. Hay tres ubicaciones y cada una cumple una función:

🌐 GitHub: repositorio remotogithub.com/elumbreras23-creator/elumbreras23-creator.github.io
↓ git pull   /   ↑ git push
📁 Repositorio Git de MAX 12/home/madrid/mi-web-github/
↕ copiar archivos con precaución
🖥️ Servidor Apache local/var/www/html/

Git sincroniza el repositorio remoto con la carpeta que tiene Git. No copia por sí solo los cambios a /var/www/html/.

La web pública se sirve desde GitHub Pages. La web de pruebas se sirve desde Apache en http://localhost/.

2. Antes de sincronizar: comprobar el estado

Abre la terminal de MAX 12 con tu usuario habitual, madrid:

cd ~/mi-web-github
git status

Si aparece nothing to commit, working tree clean, el repositorio Git local no tiene modificaciones pendientes. Eso no significa que Apache esté idéntico: la carpeta de Apache está fuera del repositorio.

Importante: si has editado archivos en Geany dentro de /var/www/html/, no los sobrescribas todavía con los de GitHub. Guarda primero una copia de los archivos afectados o revisa las diferencias.

Comprobar diferencias antes de copiar

diff -u /var/www/html/entradas.js ~/mi-web-github/entradas.js

Si diff no muestra nada, los archivos coinciden. Si muestra líneas con - y +, son diferentes. También puedes comparar index.html y entradas.json.

3. Recibir los cambios hechos directamente en GitHub

Imagina que has eliminado el botón «Volver al blog» desde el editor de GitHub o que has actualizado entradas.js para agrupar publicaciones por día.

  1. Comprueba que el repositorio local no tiene cambios pendientes ejecutando git status.
  2. Descarga y aplica las actualizaciones de la rama main:
cd ~/mi-web-github
git pull --ff-only origin main

pull trae las modificaciones de GitHub. La opción --ff-only impide crear una fusión automática si las historias han divergido.

Si el comando termina correctamente, tu carpeta ~/mi-web-github/ ya está actualizada. Todavía falta actualizar Apache.
Si falla el pull: no utilices git reset --hard, git push --force ni copies archivos indiscriminadamente. Revisa primero git status y el mensaje de error.

4. Llevar los cambios a Apache local

Solo cuando hayas confirmado que no necesitas conservar versiones diferentes que estén en Apache, copia las versiones actualizadas desde Git:

sudo cp ~/mi-web-github/index.html /var/www/html/
sudo cp ~/mi-web-github/entradas.js /var/www/html/
sudo cp ~/mi-web-github/entradas.json /var/www/html/

Si también has modificado las prácticas en GitHub:

sudo cp ~/mi-web-github/publicaciones/*.html /var/www/html/publicaciones/

Estas órdenes sustituyen los archivos de destino que tengan el mismo nombre. No eliminan otros archivos de Apache y no tocan las carpetas de Moodle o WordPress, pero sí pueden sobrescribir tus cambios no sincronizados.

Comprueba el resultado en http://localhost/. Si ves una versión antigua, fuerza la recarga con Ctrl + F5.

5. Crear una entrada nueva y publicarla

Una vez sincronizadas las tres copias, puedes volver a tu forma habitual de trabajo:

  1. Crea la página HTML en /var/www/html/publicaciones/ utilizando Geany.
  2. Añade el objeto de la entrada al archivo /var/www/html/entradas.json y conserva la sintaxis correcta del JSON.
  3. Abre http://localhost/, comprueba el índice y pulsa el enlace de la nueva publicación.
  4. Copia al repositorio Git únicamente lo que has modificado:
cd ~/mi-web-github
cp /var/www/html/entradas.json .
cp /var/www/html/publicaciones/mi-nueva-entrada.html publicaciones/

El nombre mi-nueva-entrada.html es un ejemplo: debes sustituirlo por el nombre real del archivo.

Después comprueba, confirma y publica:

git status
git add entradas.json publicaciones/mi-nueva-entrada.html
git commit -m "Añadir nueva entrada al blog"
git push origin main

El push envía los cambios a GitHub; GitHub Pages actualiza la web pública cuando termina el despliegue. Compruébala en elumbreras23-creator.github.io.

¿Y el script publicar-web? Puedes usarlo para publicar, pero su versión inicial copia archivos desde Apache antes de verificar los cambios remotos. Por eso, primero debes sincronizar y resolver diferencias. En el futuro podemos mejorarlo para que compruebe esto automáticamente.

6. ¿Y si he modificado cosas en ambos sitios?

Hay que distinguir dos situaciones:

SituaciónQué conviene hacer
Solo has editado en GitHubgit pull --ff-only y, tras revisar, copiar a Apache.
Solo has editado en ApacheCopiar al repositorio, revisar, commit y push.
Has editado archivos distintos en los dos lugaresRecibir primero los cambios remotos y copiar después solo los archivos locales nuevos o editados.
Has editado el mismo archivo en GitHub y ApacheComparar las versiones y combinar los cambios manualmente antes de sobrescribir.

Consulta útil: diferencias de una página

diff -u /var/www/html/publicaciones/practica03-ut02.html \
  ~/mi-web-github/publicaciones/practica03-ut02.html

Una recomendación: si no tienes claro cuál de las dos versiones conservar, haz una copia de seguridad de ambas antes de continuar.

Un repositorio limpio no es suficiente: git status solo vigila los archivos de ~/mi-web-github/; no detecta cambios que has hecho directamente en /var/www/html/.

7. Resumen: el método que seguiremos

  1. Actualizar: comprobar el repositorio y ejecutar git pull --ff-only origin main.
  2. Sincronizar Apache: revisar las diferencias antes de copiar los archivos.
  3. Editar: crear tu nueva práctica HTML y actualizar entradas.json.
  4. Probar: verificar la web en http://localhost/.
  5. Publicar: copiar las novedades al repositorio, hacer git commit y git push.

Lista de comprobación antes de publicar

  • He comprobado los cambios de GitHub y de Apache.
  • La entrada abre correctamente en localhost.
  • El JSON incluye el título, fecha, descripción y URL correctos.
  • No estoy incluyendo datos personales ni archivos que deban permanecer privados.
  • He revisado git status antes de confirmar los cambios.
  • He comprobado el resultado en la web pública.
